Six principles behind this design

Every decision below derives from one of these.

  • 1. One brain, many surfaces: AGI is the only brain. The site widget, the customer bot, the admin bot, the TWA and the web panel are all "faces" of it — no second copy of bot logic exists anywhere.
  • 2. One address, one place: the live brain is zenovix-production.up.railway.app (verified). The current deployment references it only in the widget's two embed URLs — adding a custom domain later (Railway → Settings → Custom Domain, e.g. agi.zenovix.ae) means future cloud migrations become a DNS change only.
  • 3. Graceful degradation: every dependency has a fallback step (LIVE → KB → SIM) — the site never shows an empty chat.
  • 4. Data only in durable places: Postgres/Redis/R2; a cloud's ephemeral filesystem is never the source of truth.
  • 5. Secrets only in env: no token in git, in the widget, or on cPanel.
  • 6. Scale without rewrite: AGI is stateless — state lives in PG/Redis; tomorrow 2–3 replicas behind Railway's LB with zero code change.

Instant Telegram alert to the manager(s) TELEGRAM_ADMIN_IDS — "New website lead ZX-…"

Manager reviews and decides in panel / TWA / admin bot real HITL queue in Redis/PG — with timeouts and safe claiming
7
Outcome reaches the customer and stays in audit & reports "approved/rejected" messages verbatim + full PG record

The resilience ladder — when things break

Principle 3: graceful degradation. A normal user should never notice.

RungScenarioSystem behaviorUser experience
T0 normaleverything upwidget → AGI; catalog/orders/chat all real🟢 LIVE badge + ZX references
T1LLM down/slowAGI falls back to the approved KB (existing code behavior)slightly more generic answers, no outage
T2Railway downwidget: chat → (optional) cPanel fork → built-in trilingual knowledge; shop → SIM mode; orders persist in localStorage with pendingRefchat still answers; 🔵 SIM badge; no raw errors
T3 (v3.3)Railway returnsauto-sync of queued orders (the widget-side Outbox pattern) → converted to ZX"your earlier request was registered" — nothing lost
🔔 Observability: Docker's internal healthcheck (every 30s → auto-restart) + a free external monitor (UptimeRobot) on /healthz every 5 min → email/Telegram alerts. T2 gets discovered in minutes, not by customer complaints.

7

Data, backups, monitoring

  • Single source of truth: Postgres — customers, tickets, catalog, permissions, audit. Redis holds only transient state (rates, queues, HITL locks).
  • Daily backups: Railway automatic snapshots + a scheduled pg_dump into the same R2 (a tiny worker service or a free external cron). Test restores once a month.
  • Conversations: logged in PG (LOG_TO_DB) — analyzable in the panel's analytics; replaces the fork's jsonl.
  • Retention: audit is append-only; older data archives to R2 (AGI's own archive module).
  • Monitoring: healthz (internal) + UptimeRobot (external) + Railway metrics; alerts to the manager's Telegram.

Execution roadmap — 5 phases

Full checklists live in deployment-guide.html — this is the summary.

  • Phase 0 — prep (30 min): CORS patch → GitHub · Railway account linked to the repo · DNS plan for agi.
  • Phase 1 — deploy the brain (1 h): variables from the READY.env + plugins (Postgres/Redis/Bucket) · custom domain · test /healthz, /api/public/site, /api/public/catalog?lang=fa · Telegram setWebhook.
  • Phase 2 — switch the site widget (15 min): embed code with zenovix-production.up.railway.app (already the default) · run the 8-point test (chat, catalog, order→ZX+alert, FA/mobile).
  • Phase 3 — admins & team (30 min): /admin bootstrap login → real users → rotate bootstrap · TWA menu button · UptimeRobot + daily PG backup.
  • Phase 4 — hardening (optional, v3.3): widget failover chain (api → cPanel fork → local KB) · outbox sync of offline orders · WhatsApp/email channels via Twilio/SendGrid.
